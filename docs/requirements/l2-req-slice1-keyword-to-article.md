## 要求（スライス1の exact scope）

### R1. キーワード入力 — サイト設計データの取り込み（改訂 2026-08-22）

入力は単なる KW リストではなく **PO のサイト設計 Excel**（実物 3 ファイルで形式確認済み:
大人のひとりビジネスラボ.xlsx／IT就活大学キーワードマップ.xlsx／競合メディアキーワード獲得状況.xlsx）。
設計データは 2 層で扱う:

- **人間の戦略層（正本として取り込む）**: サイトコンセプト（ビジョン・キャッシュポイント・
  カテゴリコンセプト）／カテゴリ階層（親・子・孫）／**メインキーワードの割り当て**
  （+検索 Vol・優先度・検索意図・「完了」進捗マーク）。ここはハーネスが上書きしない。
- **仮置きの詳細層（ハーネスが実データで置換・生成する）**: サブ KW 展開・記事単位の
  KW セット。取り込み時は参考値扱いとし、**詳細設計は DFS サジェスト+SERP グルーピング+
  PAA から機械生成**する（＝人間が手作業でやっていたサブ展開の代替が本スライスの中核価値）。

取り込み契約:
- 対象シートとキーワード列はヘッダー行（`キーワード`／`メインキーワード` 等）で自動判別。
  ヘッダー不在シート（コンセプト等）はメタデータとして原文保持。
- 正規化: 前後空白除去のみ（表記ゆれは SERP グルーピングで同一判定するため原文保持）。
  重複 KW は先勝ち+警告記録。空欄 KW 行はスキップ+警告。読めないファイルは fail-close。
- 競合獲得状況ファイル（KW・順位・Vol・難易度・URL・トラフィック・検索意図）は
  **ギャップ分析の入力**（競合獲得×自マップ不在×低難易度の優先候補を決定論ソート）と、
  SERP グルーピング・意図分類の検証データセットに使う。
- 補完として、キーワード候補の収集ができる: ラッコキーワード等の無料車線サジェスト／
  DataForSEO（以下 DFS）によるサジェスト取得・SERP 競合の獲得キーワード取得。

### R2. キーワード解析（分析基盤の事前処理 = ガードレール機構）

キーワード解析は記事生成の前提となる**ガードレール機構**として機能させる。
生成に先立ち、確定キーワード群を解析してまとめる事前処理を置く。

**戦場選定の原則（PO 定義 2026-08-22）**: 戦略とは優位な戦場で素早く簡単に勝つことであり、
リサーチ・事前処理はその準備で**本番（執筆）にリソースを割かない**ためにある。
KW を全部施策するのではなく、**記事が適切に KW を持つ**ことが大事。前処理は 4 段:

1. **足切り**: 施策しない KW を先に確定する（意図不明・サイトコンセプト非整合・勝ち目のない
   SERP・季節切れ等）。**捨てた KW と理由も証跡化**し R6 で監査可能にする。
2. **統合**: 同一 SERP クラスタは 1 記事へ（分散は自己競合）。
3. **戦場選定**: 記事候補を「勝ちやすさ×価値」（難易度・Vol・自サイト資産との整合）で
   決定論ソートし、優位な戦場から着手する。全 KW 消化を目標にしない。
4. **記事への割り当て**: 施策・監査の単位は KW でなく**記事**。記事がメイン KW+サブ KW 群+
   PAA を保有する構造とし、R6 ダッシュボードの主役も記事単位とする。

執筆は前処理の成果物（構成案・共通見出し・エビデンス・テンプレ）を組み立てる軽工程とする。

品質の 2 線を定義する（PO 定義 2026-08-21）:

- **キープライン**: 必須（決定論ゲート — 同一 SERP 統合・PAA・共通見出し）を落とさないこと。
  fail-close で守る最低線。
- **品質ライン**: 仮説（検索シチュエーション・ターゲット・打開の提示）の精度を
  レビュー検証の積み重ねで上げていくこと。継続改善の線。

- 確定キーワード群の SERP データは **DFS から取得**する（L1 採用境界 4/7 の範囲内:
  standard キュー・結果キャッシュ・呼び出し上限 config・低頻度バッチ）。
- 解析は決定論（L1 中核機能: AI は生成・提案のみ。グルーピング・判定は計算で導く）。
- **ガードレール・ファースト検証**（生成前チェックの初期セット）:
  - 同一 SERPs（検索意図が同一）のキーワード群が 1 記事に統合されているか
    （分散していたら統合を要求する）。
  - PAA（People Also Ask）が記事構成にカバーされているか。
  - **競合の共通見出し**（下記）が記事構成にカバーされているか。
- **競合見出し比較**（PO 追記 2026-08-21）: SERP 上位の競合ページから見出し構成を取得し
  （取得は L1 段階方式の①単発 HTTP fetch — SERP で得た既知 URL のみ）、2 層で扱う:
  1. **決定論ゲート**: 競合間で共通するテーマの見出し＝「外したらいけないもの」を
     計算で抽出し、カバー必須のガードレールとする。
  2. **仮説レビュー検証**: 共通外の見出しについて、1 位と「1 位になれないページ群」の
     差分から仮説を立てる。仮説の観点は**検索シチュエーションとターゲット**を主とし、
     「打開（悩みの解決）をどう提示しているか」を見る。仮説は AI が生成し、
     判定の正本にはしない — レビュー（PO／実測）で検証して採否を決める。
- **仮説層・検証設計の思想正本**（追加 2026-08-22）: PO 資料
  「若手マーケターのためのリサーチスキル」（poc-wp data/）を仮説レビュー層の設計出典とする。
  - セグメント=属性でなく**環境圧**で切る（同一 SERP グルーピング=同一環境圧の近似、の理論根拠）。
  - 仮説は「発見→仮説（一文で言い切る）→施策→検証」の 4 段で生成し、
    **「どの行動が増えれば正しいと言えるか」を公開前に記事メタとして先決め**する
    （⑤リライトの判定を当たり外れでなく学習にする）。
  - 検証は「データ（数字）×行動（ログ）×声（知恵袋・レビュー・コメント）」の三面。
  - 競合参照は「表面コピー禁止・構造理解→自社化」— 生成プロンプトの禁止規則に含める。
- SERPs は変動するため、対処時（ガードレール違反の裁定・疑義時）は**有人ブラウザ・
  シークレットモードで実 SERPs を確認**する。
- **エビデンスゲート**（PO 採用 2026-08-21）: 記事中の検証可能な事実（数値・固有名詞・
  価格・日付）は **AI に生成させず、出典 API から取得した値をパイプラインが埋め込む**。
  ゲート判定は「全事実項目に出典（provenance）が紐づいているか」の決定論チェック。
  出典に使う無料 API: e-Stat（統計数値の正本）／openBD・NDL（書誌）／楽天・Amazon
  PA-API（商品・価格 — 取得時点明記を規則に含む）／YouTube Data API（動画メトリクス）／
  GSC・GA4（自サイト実績）／Wikipedia・Wikidata（定義・エンティティ — 引用可だが数値の
  単独正本にはしない）／e-Gov 法令 API（条文の正本。**事実引用まで — 法解釈・個別の
  あてはめは書かない**をゲート規則に含む。国会会議録 API も政策系一次情報として利用可）。
  推定値（DFS 検索ボリューム等）を書く場合は「推定」表記を必須とする。
  本スライスでは規則の確立まで（プレーン本文に事実を書く場合に適用）。埋め込みパイプラインの
  実装強化は ② 以降。

### R4. アーキテクチャ原則 — 中間 JSON（PO 承認 2026-08-22）

記事は**テーマ非依存の中間 JSON**（意図語彙のセクション列: h2/h3/p/list/point/attention/
faq/steps/button/table/balloon 等）を正本とし、AI は中間 JSON だけを出力する。
マークアップはテーマ別レンダラ（決定論）が組み立てる。

- 効果: AI 出力は正味の情報量のみ（トークン効率・ブロック破損防止）。テーマ差は
  レンダラのアダプタで吸収（SWELL=収穫マークアップ準拠／JIN:R=スロット・ブロック／
  HELIX Neo=当面 core 縮退、意図語彙が HELIX Theme ブロック開発のロードマップになる）。
- **逆変換**（既存記事→中間 JSON）も同一語彙で成立させる。② の装飾・CV 理解は
  逆変換の type 分布で決定論集計、⑤ のリライトは「逆変換→JSON 差分修正→再レンダリング」。
- 未対応 type のレンダリングは fail-close。逆変換の未知ブロックは raw 保全（可逆性優先）。
- PoC 証跡 2026-08-22（poc-wp）: レンダラ v0 で 9 ブロック種認識、実記事 40KB→130
  セクション・未対応ゼロ、ラウンドトリップ完全復元。
- **正式化要件（sol レビュー反映 2026-08-22、L3 設計の必須入力）**:
  - 中間 JSON は **JSON Schema で正本化**し `schema_version` を必須フィールドとする。
    required/型制約/未知フィールド規則（未知 type は投稿前 fail-close・逆変換では raw 保全）を定義。
    語彙に `postlink`（内部リンク参照）を正式追加（逆変換実測で出現済み）。
  - **エビデンスゲートの構造**: 事実値は素の文字列でなく
    `{value, source: {api, ref, fetched_at}, estimated: bool}` の provenance 付き構造で持つ。
    ゲート判定=全事実ノードに source があること。
  - **エディタ妥当性**: parse_blocks 通過だけでは不十分（実測: 手書き faq/step/button が
    Gutenberg で invalid 警告）。レンダラのテーマブロックは**収穫マークアップ準拠を必須**とし、
    受入にエディタ妥当性ゲート（Playwright で block-editor-warning ゼロ）を含める。

### R5. ライティングレギュレーション — 文体・構成の決定論ゲート（追加 2026-08-22）

出典: PO の実運用 SOP「大人のひとりビジネスラボ｜ライティングレギュレーション.xlsx」
（人間ライター向け規程をハーネスの機械ゲートへ昇格。poc-wp data/ に格納）。

- **構成規則（生成時に強制・ゲートで検査）**: タイトルは 36 字以内・メイン KW を先頭 13 字
  以内に含める・タイトル案は 3 つ生成し PO/ガードレールで選定。見出しは番号形式
  （`1.` `1-1.`）・H4 まで（積極利用は H3 まで・H4 に番号なし）。見出しは競合共通テーマ+
  オリジナル切り口で CV 発生ストーリーに整理する。
- **文体規則（中間 JSON 上で決定論 lint）**: リード文 300〜500 字／H2 単体 500 字程度／
  H2+H3 セットは H2 リード 150 字+H3 リード 300〜400 字。ですます調・文末「です/ます」
  3 連続禁止・1 文 40〜60 字（最大 90 字）。箇条書き・表は文字数カウント外・
  箇条書きは H3 あたり原則 1 回。
- **調査 SOP の機械化対応（L3 設計の仕様正本）**: 上位 **5** 記事のタイトル/見出し/内容調査
  =共通見出しゲート・AIO 調査=DFS `ai_overview`・ニーズ調査=PAA+**Yahoo!知恵袋 単発 fetch**
  （補完車線として追加）・ソーシャルリスニング=ブラウザ車線（defer 可）・
  読者像→ターゲット→共感→世論スタンス（同調/反論）=仮説レビュー層の生成プロンプト仕様。

### R6. 施策ダッシュボード — PO 監査基盤（PO 要求 2026-08-22）

ダッシュボードは進捗表示ではなく、**PO が AI の仕事の適切性を監査し、判断を最速で
フィードバックするための基盤**。UI に出せる情報＝ハーネスが証跡化できている情報であり、
**UI の完成度をハーネスの完成度の測定器とする**。

必須 7 ビュー:

1. **KW 一覧・施策状況**: 全 KW×状態×記事の対応（設計 JSON+状態 DB）。
2. **処理の適切性**: 各 KW の処理中身を開ける — SERP グルーピング結果・共通見出し・構成案・
   仮説・各ゲート判定の理由と入力証跡。PO が「この判断は違う」と指摘できる粒度。
   **KW グルーピングの監査**（PO 追記 2026-08-22）を含む: クラスタ一覧（KW 群→1 記事の
   対応・代表 KW・合算 Vol）／判定根拠（ペア別 SERP 重複率を数字で開示）／閾値際の
   境界ケースに要注意フラグ／**PO の分割・統合・除外操作**（上書きは証跡化し再解析後も
   機械判定より優先）。初期精度は手作業 15 トピック分類・検索意図ラベルとの一致率で表示。
3. **AIO/LLMO 打ち手**: KW 別 AI Overview 出現（DFS ai_overview）・llms.txt 状態・
   AI クローラー巡回・打ち手の提案と実施状況。
4. **内部リンク構造の可視化**: リンクグラフ（孤立記事・ハブ・カテゴリ間導線）。
5. **リライト状況**: 記事×版履歴×ゲート再判定×「何が増えれば勝ちか」メタの達成状況。
6. **成果状況**: GSC/GA4 取り込み値・収益・記事別勝敗判定（成功基準の決定論実測）。
7. **カレンダー**: 公開予定・外部通知（投稿・更新・展開）のタイミングと実績・季節性。

横串の原則:
- **表示される全ステータスは実行証跡に由来する**（手動書換禁止。gate_runs への書き込みは
  ゲート実行器のみ・実行ログと入力 digest を必ず紐づける）。
- 記事実体（中間 JSON）はバージョン管理し、版間 diff を UI で見せる（GitHub 的仕組み）。
- 承認・差し戻しは UI 操作として実装し、操作自体を証跡化（承認正本= L1 の UI フロント）。
- L3 では**ダッシュボードを最初のモジュール**とし、パイプラインの各段が動くたびに
  対応ビューが埋まる順で実装する（PO の監査が初日から効く構成）。
- 非捕捉 3 点セット+認証（承認操作を入れる段階で必須）。

## PoC（進行順序: PoC → 要求確定 → 設計 → 実装）

実装前に実機証跡を残す 3 点:

| # | PoC | 確認内容 |
| --- | --- | --- |
| PoC-1 | ブロックコメント REST 投稿 | ブロックコメント形式 HTML を WP REST で投稿し、エディタ・表示で正しく成立するか（プレーン HTML との差分も記録） |
| PoC-2 | 装飾パーツ抽出・操作 | 既存記事から装飾パーツを抽出できるか／そもそも REST 経由で操作できるか（② の先行検証）。抽出経路は SSH + WP-CLI で生 `post_content`（ブロックコメント付き HTML）を直接取得する前提とし、PoC-1 と合わせて抽出→再投入のラウンドトリップで検証する |
| PoC-3 | キーワード解析データ取得 | DFS standard キューでサジェスト・SERP・PAA が取得でき、同一 SERP 判定の入力になるか（コスト実測を含む）。SERP 上位 URL への単発 fetch で見出し構成（h タグ）が抽出でき、共通見出しの決定論抽出の入力になるか |

## 人間受入基準（candidate）

0. **スライス①の成果物定義（PO 確定 2026-08-22）**: 「キーワードから記事を書ける基盤」とは
   R6 ダッシュボード込みの全体を指す。記事 1 本の公開は、**ダッシュボード上で全工程
   （KW 取り込み→グルーピング→解析→ゲート→承認→公開）が証跡つきで監査可能な状態**で
   達成されて初めて受入となる（画面に出ない処理・証跡に由来しない表示は未完成扱い）。

1. PO 提示の Excel キーワードから、ガードレール検証（同一 SERP 統合・PAA カバー・
   **競合共通見出しカバー**）を通過した記事 1 本が solobiz-lab.com に公開される
   （パイプライン一気通貫）。共通見出しの判定規則（sol レビュー反映 2026-08-22）:
   SERP 上位 10 のうち記事型ページ（EC・Q&A・求人等を除外）を対象に、助詞分割トークンが
   **過半数のサイトに出現する語をカバー必須テーマ**とする。対象記事型ページが 3 未満の
   キーワードは共通見出しゲートを「判定不能」として fail-close（自動生成へ進めず PO 裁定）。
2. 解析結果（キーワードグルーピング・PAA・ガードレール判定）が決定論の成果物として
   残り、同じ入力から同じ結論が再現できる。
3. DFS 呼び出しがキャッシュ・上限 config の統制下にあり、費用実測が記録される。

## 非対象（本スライス）

- ロードマップ ②〜⑥（装飾・内部リンク・売り場・GSC/GA4 解析）。
- 新規サイト立ち上げ・HELIX-WP-THEME 構築・スケジュール自走・UI フロント・収益計測。
- 自前クローラー（L1 明示 defer のまま）。競合本文の閲覧は L1 の段階方式
  （単発 fetch → ブラウザ → DFS Content Parsing）に従う。

## L3 設計への引き継ぎ事項（sol レビュー 2026-08-22 の中優先項目）

- 外部ページ fetch のセキュリティ: SSRF 対策（プライベート IP 拒否）・リダイレクト上限・
  応答サイズ上限（3MB 実装済みを契約化）・**取得 HTML を AI 入力に渡す際のプロンプト
  インジェクション対策**（見出しテキスト等の構造化抽出のみ渡し、生 HTML を渡さない）。
- 競合見出しの保存は解析目的の内部利用に限定（転載しない）。PA-API 利用時は価格の
  取得時点明記・キャッシュ 24h 制限等の規約条件を実装契約に含める。
- 製品 L1（HELIX Theme）との境界: 中間 JSON の保存正本はハーネス側 DB。公開 on/off・
  ナレッジ公開（機能候補④）はテーマ側 config で、ハーネスは書き込むだけ（同期責任はハーネス）。
- リポ運用: L3 実装開始時に media/wp へ本家 GitHub 運用の軽量版を継承
  （main ブランチ保護・PR 必須・CI green 必須。ドキュメントのみの現段階は直 push 継続）。

## L1 未決事項との対応

| L1 未決事項 | 本スライスでの扱い |
| --- | --- |
| DFS の「重点セット」「低頻度」 | **確定（実測 2026-08-22 に基づく初期値）**: SERP standard $0.0006/クエリ・サジェスト $0.0138/回。重点 KW 上限 **100**・SERP 取得周期 **週 1**・サジェストは KW 追加時のみ。キャッシュ TTL: SERP 7 日／サジェスト 30 日（同一入力の再取得ゼロ） |
| API 費用の上限 | **確定（初期値）**: DFS 月次上限 **$5**（config 値・超過時は取得停止+PO 通知の fail-close。想定消費は月 $1 未満）。画像生成は codex-imagen（ChatGPT Pro 枠内・追加課金なし）、出典 API は無料枠のみ。AI プロバイダ費用は実装後最初の 10 記事で 1 記事あたり実測し KPI 化する |
| 無人ブラウザのリスク分類 | 不要（本スライスのブラウザ利用は有人シークレットモードのみ）— defer 継続 |
| GSC フィルター・UI フロント・主サイト影響・標準プラグイン・KPI・売上算定 | 本スライス非対象 — defer 継続（⑤⑥・後続スライスで確定） |
