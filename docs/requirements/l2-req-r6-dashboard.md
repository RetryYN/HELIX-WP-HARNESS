# L2 要求 — R6 施策ダッシュボード（詳細要求）

- 位置づけ: `l2-req-slice1-keyword-to-article.md` R6 節の詳細化。本書が R6 の正本であり、
  スライス1 文書の R6 節は概要+本書への参照とする。
- 状態: **candidate**（2026-08-22 起草。sol レビュー→PO 確認で confirmed へ）
- 前提決定（PO 判断 2026-08-22）: SQLite ハブ／軽量 SaaS 型（HTTPS+認証）／
  スマホ=承認判断・PC=深掘り分析／入口=要承認キュー。

## 1. 目的と完成度定義

ダッシュボードは進捗表示ではなく **PO が AI の仕事の適切性を監査し、判断を最速で返す基盤**。

- 表示される全ステータス・全数値は**実行証跡に由来**する。UI に出せる情報＝ハーネスが
  証跡化できている情報であり、**UI の完成度がハーネスの完成度の測定器**。
- 完成度の判定は「見た目が整っている」ではなく次の 3 条件で行う:
  1. **証跡由来性**: 全表示フィールドが §2 のデータ契約（表×書き込み主体）に対応づく。
     対応のない表示は実装不備。
  2. **状態網羅**: 全画面が空・読込中・エラー・stale の 4 状態を明示的にデザインして持つ
     （データがない画面が「白紙」で出るのは不備。「なぜ空か+次に何が起きるか」を表示する）。
  3. **判断到達速度**: PO の主要な問い（各画面の §3「問い」）に 2 クリック以内で到達できる。

## 2. データ契約（SQLite ハブ）

単一 SQLite ファイルを正本とする。**書き込み主体を表ごとに 1 つに限定**し、
UI は読み取り+操作証跡の追記のみを行う。

| 表 | 内容 | 書き込み主体 | UI の権限 |
| --- | --- | --- | --- |
| keywords | KW 原本（R1 取り込み結果、出典ファイル・行の参照つき） | 取り込みモジュール | 読み取り |
| clusters | SERP グルーピング結果（ペア別重複率・代表 KW・境界フラグ） | 解析モジュール | 読み取り |
| articles | 記事レジストリ（メイン KW・状態・WP post id・URL） | パイプライン | 読み取り |
| article_versions | 中間 JSON の版（全文格納・schema_version・生成入力 digest） | パイプライン | 読み取り（版間 diff 表示） |
| gate_runs | ゲート実行（種別・入力 digest・判定・理由・実行ログ参照） | ゲート実行器のみ | 読み取り |
| operations | PO 操作証跡（承認・差し戻し・クラスタ上書き・却下理由） | **UI のみ** | 追記 |
| programs | ASP 提携（provider・単価・成果発生条件・EPC・確定率・状態・取得日） | A8 取り込み | 読み取り |
| article_links | 記事×リンク対応（内部リンク・提携プログラム ID） | 解析モジュール | 読み取り |
| results_gsc / results_a8 | 週次 CSV 取り込み値（取得日・期間窓つき） | CSV 取り込み | 読み取り |
| crawler_hits | AI クローラー巡回集計（⑦） | ログ解析 | 読み取り |
| ingest_runs | 取得ジョブ実行記録（cron/手動・成否・対象期間） | 各取り込み | 読み取り |

横串規則:

- 状態遷移（下書き→承認待ち→公開 等）は articles の状態列を直接書き換えるのではなく、
  gate_runs / operations からの**導出**として実装する（履歴の改竄不能性）。
- 全取り込みデータは取得日+期間窓を必須列とし、UI は鮮度を常時表示（2 周期超で stale 警告）。
- 記事正本（中間 JSON）は article_versions に置き、執筆・レンダリング・逆変換は
  DB から fetch する（PO 判断: SQLite で画面をつなぎ、記事データは JSON で fetch）。

## 3. 画面要求

各画面を「PO の問い」から定義する。表示項目は §2 の表に対応づく（括弧内がデータ源）。

### 3.1 ホーム（入口 — 要承認キュー）

- **問い**: 「今、俺の判断が要ることは何か」「運転は正常か」
- 表示: 要承認キュー（operations 待ち: 記事承認・境界クラスタ裁定・提携申請候補）を最上部。
  各項目に判断要約 = 何を・なぜ（ゲート判定と理由: gate_runs）・リスク。
  警告帯: stale データ（ingest_runs）・提携切れ検知（programs 差分）・ゲート失敗。
  直近の成果ハイライト（results_*）。
- 操作: 承認／差し戻し（理由必須）→ operations へ追記。
- 受入: キュー 0 件時に「運転正常+次の自動実行予定」が表示される（白紙にしない）。

### 3.2 KW・記事一覧

- **問い**: 「どの記事（戦場）がどこまで進んでいるか」「捨てた KW はなぜ捨てたか」
- 表示: **記事が主役**の一覧（articles）。各記事にメイン KW+サブ KW 群+PAA（keywords,
  clusters）、状態バッジ（gate_runs/operations 由来のみ）、公開 URL。
  足切り KW の墓場ビュー: 捨てた KW×理由（R2 の証跡化要求と対応）。
- 操作: なし（読み取り）。詳細へ 1 クリック遷移。
- 受入: 状態バッジに手書き値の混入経路が存在しない（スキーマ上不可能であること）。

### 3.3 処理の適切性（グルーピング監査）

- **問い**: 「この KW 処理・クラスタリングは正しいか」「境界ケースはどれか」
- 表示: クラスタ一覧（clusters: KW 群→記事対応・代表 KW・合算 Vol）。クラスタを開くと
  判定根拠 = ペア別 SERP 重複率の数字・閾値・境界フラグ。共通見出し・構成案・仮説と
  各ゲート判定（gate_runs: 入力 digest つき）。
- 操作: クラスタの分割・統合・KW 除外（operations。機械判定より優先・再解析後も維持）。
- 受入: 任意のクラスタについて「なぜこうグルーピングされたか」を数字で答えられる。

### 3.4 AIO / LLMO

- **問い**: 「AI に読まれているか」「AI 露出の打ち手はあるか」
- 表示: KW×ai_overview 出現（DFS 取得値）、llms.txt 状態、AI クローラー巡回推移
  （crawler_hits — ⑦の接続点。未実装期間は「未計測」と明示）。
- 操作: なし（打ち手提案は承認キュー経由）。

### 3.5 内部リンク・売り場

- **問い**: 「リンク構造に穴（孤立・断絶）はないか」「どの記事がどの案件を持つか」
- 表示: リンクグラフ（article_links: 孤立記事・ハブの視認）。
  記事×提携プログラム対応表（programs 結合: 単価・**成果発生条件・EPC・確定率**・状態）。
  提携切れの影響記事リスト（terminated 差分×article_links）。
- 操作: 差し替え候補の承認（operations → 実行はパイプライン）。

### 3.6 リライト

- **問い**: 「どの記事を直すべきか」「直した結果どうなったか」
- 表示: 記事×版履歴（article_versions）→ 版間の**構造 diff**（中間 JSON セクション単位）。
  「何が増えれば勝ちか」メタ（公開前に先決めした検証条件）の達成状況（results_gsc）。
  リライト候補の決定論ソート（表示回数あり×低順位等 — 閾値は⑤で確定、それまで参考表示）。
- 操作: リライト承認（operations）。

### 3.7 成果

- **問い**: 「稼げているか」「どの記事が勝っているか（クリック非依存で）」
- 表示: 表示回数／AI 露出／CV 発生／収益を**分離した第一級指標**として表示
  （クリック・順位は補助）。記事別勝敗判定（先決め条件の実測）。A8 成果と GSC 表示の
  記事単位の突合。全数値に取得日・期間窓を併記。
- 操作: なし。

### 3.8 カレンダー

- **問い**: 「今週何が起きる/起きたか」
- 表示: 公開予定・公開実績・cron 実行予定/結果（ingest_runs）・季節性メモ。
- 操作: なし（予定変更は後続スライス）。

## 4. UI 品質基準（「雑な UI」の禁止規定）

- **デザイントークン**: 色・余白・タイポグラフィをトークンで一元定義（HELIX Theme の
  JSON トークン思想と同型）。場当たりの inline style を持ち込まない。
- **状態の網羅**: §1-2 の 4 状態（空/読込/エラー/stale）を全画面で設計。エラーは
  「何が失敗し、どの証跡を見ればよいか」を表示する。
- **操作の安全**: 破壊的操作なし（全て追記）。承認・差し戻しは確認ステップ+理由入力。
  操作結果は即座に画面へ反映され、operations の証跡 ID を表示する。
- **レスポンシブ**: スマホ幅ではホーム（承認キュー）を最適化、深掘り画面は PC 幅を
  前提に設計してよい（無理な縮小で判断品質を落とさない）。
- **性能**: 一覧表示 1 秒以内（ローカル SQLite 読み取りで達成可能な水準を要求とする）。
- **アクセシビリティ最低線**: キーボード操作可能・状態を色のみで表現しない。

## 5. 受入基準

1. §2 の全表が存在し、UI の全表示フィールド→表・列の対応表（トレーサビリティ表）が
   設計成果物として存在する。
2. 「証跡なしでは空」の実証: 空 DB で起動した画面が全て §1-2 の空状態表示になる
   （ダミーデータの混入がない）ことを Playwright E2E で確認。
3. 実データ疎通: 稼働中の GSC/A8 週次 CSV を取り込み、成果ビュー（3.7）とホーム（3.1）が
   実データで埋まる。
4. 操作証跡: UI からの承認操作 1 件が operations に記録され、導出状態が変化し、
   画面に証跡 ID が表示される E2E。
5. スマホ幅でホーム→承認 1 件完了の E2E（判断要約が表示されること）。
6. 全画面のスクリーンショットを受入証跡として保存し、PO が画面ごとに合否を返せる。

## 6. 非対象

- 複数ユーザー・権限管理（単一 PO。将来の製品化はレイヤを分けて別企画）。
- 通知配信（メール・プッシュ — カレンダーの外部通知は表示のみ。配信は後続スライス）。
- ⑦ クローラー計測の実装（表示枠だけ用意し「未計測」表示）。
