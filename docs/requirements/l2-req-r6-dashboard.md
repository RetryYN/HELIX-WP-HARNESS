## 1. 目的と完成度定義

ダッシュボードは進捗表示ではなく **PO が AI の仕事の適切性を監査し、判断を最速で返す基盤**。

- 表示される全ステータス・全数値は**実行証跡に由来**する。UI に出せる情報＝ハーネスが
  証跡化できている情報であり、**UI の完成度がハーネスの完成度の測定器**。
- 完成度の判定は「見た目が整っている」ではなく次の 3 条件で行う:
  1. **証跡由来性**: 全表示フィールドが §2 のデータ契約（表×書き込み主体）に対応づく。
     対応のない表示は実装不備。
  2. **状態網羅**: 全画面が空・読込中・エラー・stale の 4 状態を明示的にデザインして持つ
     （データがない画面が「白紙」で出るのは不備。「なぜ空か+次に何が起きるか」を表示する）。
  3. **判断到達速度**: PO の主要な問い（各画面の §3「問い」）に 2 クリック以内で到達できる。

## 2. データ契約（SQLite ハブ）

単一 SQLite ファイルを運用正本とする。Excel・CSV・API応答は入力または観測snapshotであり、
取り込み後の状態・関係・順序の正本にはしない。**書き込み主体（writer）は表ごとに単一モジュールに固定**し
（抽象名でなく L3 でモジュール名を確定して対応表を成果物にする）、UI は読み取りと
`approval_requests` への応答（`operations` 追記）のみを行う。

### 2.5 横串規則

- **状態は導出**: 記事・KW・クラスタの状態は gate_runs / operations / pipeline_runs からの
  導出ビューとして実装し、正本表に状態列を持たない（手書き混入をスキーマ的に不可能にする）。
  導出の優先順位（PO 操作＞最新ゲート判定＞工程実行）と再解析時の regla（PO 上書きは維持）を
  L3 設計で確定し、導出 SQL 自体を成果物にする。
- **サイト分離**: 全KW・カテゴリ・解析・記事・成果・操作は`site_id`を必須とし、一覧件数、
  グルーピング、WP記事ID、内部リンク、GSCクエリをサイト横断で混在させない。UIはヘッダーで
  サイトを選択してから各機能ビューを表示する。ヘッダーに固定表示するサイトタブは最大4件とし、
  追加サイトは検索可能なサイト一覧から選択する。
- **鮮度**: 外部データ系はデータセットごとに期待更新周期を定義し（GSC/A8=週 1、
  設計 Excel=不定期〔取り込み日を表示〕、site_checks=検査日）、周期性のあるものは
  2 周期超で stale 警告。UI は全数値に取得日・期間窓を併記する。
- 記事正本（中間 JSON）は article_versions に置き、執筆・レンダリング・逆変換は
  DB から fetch する（PO 判断: SQLite で画面をつなぎ、記事データは JSON で fetch）。

## 3. 画面要求

各画面を「PO の問い」から定義する。表示項目は §2 の表に対応づく（括弧内がデータ源）。

### 3.1 ホーム（入口 — 要承認キュー）

- **問い**: 「今、俺の判断が要ることは何か」「運転は正常か」
- 表示: 要承認キュー（approval_requests の未応答分）を最上部。各項目に判断要約
  （何を・なぜ・ゲート判定・リスク — approval_requests に格納済みの要約）。
  警告帯: stale データ（ingest_runs）・提携切れ検知（programs 差分）・ゲート失敗・
  取得ジョブ失敗。直近の成果ハイライト（results_*）。
- 操作: 承認／差し戻し（理由必須）→ operations へ追記（元 approval_request を参照）。
- 受入: キュー 0 件時に「運転正常+次の定期取得予定（ingest_runs）」を表示（白紙にしない。
  記事パイプラインの自動自走はスライス1非対象のため「自動予定」は取得系のみ）。

### 3.2 KW・記事一覧

- **問い**: 「施策すべきメイン KW は何件あるか」「1記事が取るべき KW 群は何か」
  「既存記事は実際にどのクエリを獲得しているか」「期待と実績を同じ切り口で比較できるか」。
- サイト選択: すべての件数、カテゴリー、KW群、WP記事、GSCクエリを`site_id`で分離する。
  固定タブ外のサイトは検索可能なサイト一覧から選ぶ。

#### 3.2.1 キーワード一覧（期待側）

- **行の単位**: 1行=1施策KW群=1記事候補。取込KWの生行や未処理母集団を施策行として表示しない。
- **一覧列**: 親/子/孫カテゴリー、main KW、main検索Vol、内包KW件数、AIO出現有無、
  施策状態、WP記事ID、詳細導線。カテゴリーは実WP taxonomyを正本とし、存在しない深度の列は
  自動非表示にする。
- **一覧から除外する情報**: intent KW全文、SERP URL、DFS task ID、費用、gate条件は横展開せず、
  「詳細」でのみ表示する。
- **施策状態**: `未施策` / `予約済` / `下書き` / `公開中`の4値。状態は記事工程の証跡から導出し、
  WP記事IDの有無だけで推測しない。
- **フィルター**: KW検索、親/子/孫カテゴリー（親→子→孫の連動）、main KW、施策状態、
  表示件数（25/50/100/全件）、ページ送り。存在しないカテゴリー深度のフィルターは自動非表示。
- **並び**: 取込DBの`source_order`を既定とし、Excelファイル名やシート名を画面見出しに出さない。
- **カテゴリー出典**: キーワード一覧のカテゴリーは戦略層取込が完成するまで暫定推測として明示し、
  WP taxonomy由来の記事カテゴリーと同一の正本であるかのように表示しない。
- **集計**: 対象KW数、施策main KW数、未施策数、記事ID割当数をサイト単位で表示する。
- **詳細**: main選定根拠、intent KW、群内最低SERP一致数/率、共通URL、AIO観測数、施策判断、
  記事成立gate、DFS task ID、費用を表示する。単独KWは一致率0%ではなく「比較対象なし」とする。
- **自サイト記事照合**: 全施策KW群を`確定` / `タイトル一致のみ` / `複数候補` / `新規記事候補`へ分類して一覧表示する。
  詳細では候補WP記事ID、記事タイトル、タイトル一致語、28日獲得クエリ一致語を表示する。
  `確定`だけを`keyword_groups.wp_article_id`へ保存し、候補を確定IDとして表示しない。`複数候補`は
  タイトル照合候補が複数残った意味であり、同一クエリを複数記事が獲得した`カニバリ候補`とは区別する。
  メインKWの全内容語がタイトル前方（開始6内容語以内・終端10内容語以内）にまとまり候補が一意なら、GSC未獲得でも
  記事IDを確定できる。タイトルは日本語形態素解析により表層形・基本形・品詞・位置へトークン分割する。助詞・助動詞を
  含む全文法トークン列は語順・検索意図の評価用に保持し、記事ID照合では内容語の基本形トークンを使う。メインKWは
  内容語の全トークンの存在を要求する。
  単純な部分文字列一致は使わず、タイトル前方での開始位置とトークンのまとまりを評価する。関連KWの一部一致だけでは
  記事IDを確定しない。獲得クエリ一致は記事ID確定の必須条件ではなく、検索評価の実績状態として保持する。
  複数の施策KW群が同じWP記事IDへ確定しようとした場合は、獲得クエリ一致、タイトル一致長、タイトル内位置の
  順で1群だけを確定し、残りを`同一記事候補`として保留する。
  メインKWが複数記事へ一致する場合は、内包KWごとのタイトル一致およびGSCの`期待一致`/`内包一致`を補強証拠として
  記事別に集計し、支持が一意に高い記事へ絞る。内包KWの一部語だけで記事IDを確定せず、支持差がなければ`複数候補`を維持する。
  タイトルとGSCで一意にならない場合は、WP本文から抽出したH2を第三照合層として使う。H2は形態素解析後のメインKW全内容語一致、
  または2件以上の内包KW支持がある記事だけを候補とし、一意な最高支持記事だけを確定する。同点は`複数候補`を維持する。
  詳細には一致したH2本文と見出し位置を表示し、H3の一部語一致や本文一致だけでは記事IDを確定しない。
  H2でも一意にならない場合はH3を第四照合層として使い、H2と同じ全内容語/複数内包KW条件を要求する。
  H3はH2より低い重みとし、H3単独一致は`見出し一致のみ`として確定しない。タイトル・GSC・H2の既存証拠を
  補強する場合だけ候補の絞り込みに使い、H3で同点の候補は確定しない。詳細ではH2/H3の階層を区別して表示する。
  候補記事ごとに、施策KW群のメインKW＋内包KWを分母、タイトル/H2/H3のいずれかに全内容語が存在するKWを分子とする
  `構造内包率`を表示する。KWごとの最上位包含位置も併記する。単一KW群の100%やH3だけの高率では自動確定せず、
  メインKW包含の有無、照合レイヤー、次点候補との差と組み合わせて判断する。

#### 3.2.2 キーワードツリー

- サイト単位の全取込KWを形態素の基本形term multisetで階層化し、DBの`keyword_hierarchy`を正本とする。
- 同一term multisetは表記・語順alias、真部分集合のうち語数最大の実在KWを直近親とし、語数・深度・検索Volを保持する。
- UIは独立した`キーワードツリー`タブでMermaid表示し、ルートKWで絞り込める。サイトを跨いだ親子化をしない。
- 語彙親子は情報階層であり、同一記事への統合は確定しない。ツリー枝を先に確定し、その枝内でSERP群・記事照合を行う。
- `就活`と`IT就活`のように対象文脈を変える語は部分集合でも別ルートとする。IT文脈の親探索で`IT`を脱落させない。

#### 3.2.3 記事獲得クエリ（実績側）

- **行の単位**: 1行=1 WP記事ID。取得済み記事だけに限定せず、WP記事母集団と一覧件数を一致させる。
- **標準観測窓**: 過去28日（1カ月相当）を記事獲得クエリ、主クエリ選定、未観測判定の標準期間とする。
  7日窓は取得疎通・急変確認用の補助証跡に限定し、7日窓だけで「未観測」や施策不成立を確定しない。
  比較する記事群は同一の`window_days=28`と同一取得日時で揃える。
- **入力制約**: GSCを`page × query`で取得した行だけを使う。独立したページ別集計とクエリ別集計を
  推測結合しない。URLはWP RESTの実記事IDへ結合し、raw queryと共通規則によるnormalized queryを保持する。
- **一覧列**: 親/子/孫カテゴリー、記事タイトル/URL、WP記事ID、主クエリ、その表示回数・クリック・
  平均掲載順位、獲得クエリ数、取得期間/取得日時。カテゴリーは記事に実割当されたWP taxonomyを使う。
- **主クエリ**: 表示回数を基礎とし、同一サイトの実測クエリにおける表示回数p95相当でクリックを加点する対数スコア
  `ln(1+表示回数) + ln(1+クリック) × ln(1+p95表示回数)` の最大行。生CTRは少数表示で不安定なため
  主クエリ選定へ直接使わない。スコアは表示用の代表選択であり、成果判定には使わない。
- **詳細**: 記事を開くと当該期間に取得した全クエリと、表示回数、クリック、CTR、平均掲載順位を表示する。
  GSC未観測記事は一覧に残し、主クエリを「未観測」と表示する。
- **施策KW獲得照合**: 記事IDが確定した施策KW群のメインKW＋内包KWを分母とし、28日GSCクエリで
  `期待一致`または`内包一致`となったKW数を分子にして獲得率を表示する。語順違いは形態素の基本形トークン集合が
  同一なら`期待一致`、GSCクエリの内容語集合が施策KWの全内容語を包含する場合は`内包一致`とする。短いGSCクエリが
  観測されただけでは「比較」「おすすめ」等の修飾語を獲得した扱いにしない。部分文字列一致は使わない。
  詳細にはKWごとの獲得状態、対応GSCクエリ、表示回数、クリック、未獲得KW、想定外クエリを表示し、メインKW未獲得、
  獲得率50%未満、想定外表示超過を根拠とする参考リライト方針を表示する。施策KW未連携とGSC未観測は0%扱いしない。
- **フィルター**: クエリ/記事検索、親/子/孫カテゴリー（連動）、記事/WP ID、取得期間、
  表示件数（25/50/100/全件）、ページ送り。構造と配置はキーワード一覧へ揃える。
- **比較境界**: GSC未観測を流入0と断定しない。期待KW群との照合は`期待一致` / `内包一致` /
  `想定外` / `未観測` / `カニバリ候補`に分け、取得窓とGSC匿名化による欠落可能性を併記する。

#### 3.2.4 共通受入

- **母集団照合**: 取込KW総数 = 記事割当 + 未割当 + 足切り + 取込失敗 + 要確認を常時検証する。
- 一覧の全行は`source_keyword_id`からDFS task、クラスタ、WP記事ID、GSC証跡までdrill-downできる。
- DBと証跡がない場合は設計済みemptyを表示し、fixtureやページ別/クエリ別の推測値で画面を埋めない。
- 実データ版DB buildはGSC証跡を必須とし、欠落時はfail-closeする。empty-state試験だけは
  `WP_ALLOW_EMPTY_GSC=1`を明示した隔離テストとして実行し、実データPoC成功判定へ流用しない。
- required CIの既存`npm test`は100実KW/63群のDFS provenance（形態素正規化・語順alias・文脈root・語数ツリーを先に確定し、同じ枝内でSERP比較。修飾語だけの群は最寄りの実在親施策へ内包し、実在親がない群は`derived_parent_candidate`として`main_keyword`なしの未確定行で保持・表示し、記事照合・記事ID割当の対象外とする）、GSC実測attestation（28日窓・59記事/681クエリ）、
  WP見出し実測attestation（59記事・381 H2・1089 H3）、
  SQLite→API→frontend契約を検査する。GSC rawはlocal-onlyとし、集計とtree digestだけをcommitする。
- loading/error/stale/normalを区別し、データ行があるnormal状態ではemptyコンテナが余白を確保しない。
- フィルター変更時は1ページ目へ戻り、サイト変更時は両一覧のフィルターをそのサイト用に再構築する。

### 3.3 処理の適切性（グルーピング監査）

- **問い**: 「この KW 処理・クラスタリングは正しいか」「境界ケースはどれか」「機械判定は
  俺の分類とどれだけ一致しているか」
- 表示: クラスタ一覧（clusters）。クラスタを開くと判定根拠 = ペア別 SERP 重複率・閾値・
  境界フラグ+**使用した SERP スナップショットの取得条件**（取得日時・地域/端末・上位 URL 群）。
  共通見出し（heading_analyses）・構成案・仮説（hypotheses）・タイトル案（title_candidates）と
  各ゲート判定（gate_runs）。**正解データとの一致率**（cluster_truthset との比較+誤分類一覧）。
  加えて、入力したサイト設計行と DFS 実応答の対応、raw/正規化 KW、候補の由来、Vol/CPC/競合性、
  採用/保留/足切り理由、DFS task id・取得条件・取得日時・費用・snapshot digest を表示する。
- 操作: クラスタの分割・統合・KW 除外（operations。機械判定より優先・再解析後も維持）。
- 受入: 任意のクラスタについて「なぜこうグルーピングされたか」を数字で答えられる。
  任意の表示値を raw snapshot とサイト設計の元セルまで逆引きできる。fixture・手書き JSON のみで
  画面が埋まる実装は不合格とする。

### 3.4 AIO / LLMO

- **問い**: 「AIOによりorganicクリック余地が下がるKW群はどれか」「その条件でも施策する価値が
  あるか」「AI に読まれているか」
- 表示: KW×ai_overview 出現履歴・継続率（aio_observations）、AIO有無で補正した施策優先度と
  期待クリック余地、検索Vol・商業性・期待CVの併記、llms.txt 状態（site_checks・検査日つき）、
  AI クローラー巡回推移（crawler_hits — 未実装期間は「未計測」と明示）。
- 操作: なし（打ち手提案は承認キュー経由）。
- 受入: AIOは施策判断にだけ使用し、記事作成gate_runsのpass/fail条件へ混入させない。

### 3.5 内部リンク・売り場

- **問い**: 「リンク構造に穴（孤立・断絶・カテゴリ間の分断）はないか」「どの記事がどの案件を持つか」
- 表示: リンクグラフ（article_links: 孤立記事・ハブ・**カテゴリ間導線**の視認）。
  PAA・関連検索から導出したリンク候補は、起点記事、リンク位置候補、根拠語、接続先KW群、
  接続先WP記事ID、`candidate` / `waiting_for_target_article` / `placed`の状態を表示する。
  記事×提携プログラム対応表（programs: 単価・成果発生条件・EPC・確定率・状態）。
  提携切れの影響記事リスト（terminated 差分×article_links）。
- 操作: 内部リンク候補の承認・却下、差し替え候補の承認（approval_requests→operations。
  実行はパイプライン）。PAA・関連検索文字列の完全一致anchorを自動強制しない。

### 3.6 リライト

- **問い**: 「どの記事を直すべきか」「直した結果どうなったか」
- 表示: 記事×版履歴（article_versions）→ 版間の**構造 diff**（中間 JSON セクション単位）+
  **各版×全ゲートの判定変化**（gate_runs を版で結合）。「何が増えれば勝ちか」メタ
  （hypotheses）の達成状況（results_gsc）。リライト候補の決定論ソート
  （閾値は⑤で確定、それまで参考表示と明示）。
- 操作: リライト承認（approval_requests→operations）。

### 3.7 成果

- **問い**: 「稼げているか」「どの記事が勝っているか（クリック非依存で）」「L1 の成功基準に
  対して今どこか」
- 表示: 表示回数／AI 露出／CV 発生／収益を**分離した第一級指標**として表示
  （クリック・順位は補助）。記事別勝敗判定（先決め条件の実測）。A8 成果と GSC 表示の
  記事単位の突合（**帰属不能成果は別枠表示・按分しない**）。GA4 指標（未導入期間は「未計測」）。
  **L1 KPI**: 売上 ÷ 運用コスト（cost_entries）と「×2 連続 3 か月」達成状況。
  全数値に取得日・期間窓を併記。
- 操作: なし。

### 3.8 カレンダー

- **問い**: 「今週何が起きる/起きたか」
- 表示: 公開予定（publish_schedule）・公開実績（pipeline_runs）・cron 実行予定/結果
  （ingest_runs）・季節性メモ（operations 経由・出所つき）。
- 操作: なし（予定変更は後続スライス）。

## 4. UI 品質基準（「雑な UI」の禁止規定）

- **デザイントークン**: 色・余白・タイポグラフィをトークンで一元定義（HELIX Theme の
  JSON トークン思想と同型）。場当たりの inline style を持ち込まない。
- **状態の網羅**: §1-2 の 4 状態（空/読込/エラー/stale）を全画面で設計。エラーは
  「何が失敗し、どの証跡を見ればよいか」を表示する。
- **操作の安全**: 破壊的操作なし（全て追記）。承認・差し戻しは確認ステップ+理由入力。
  操作結果は即座に画面へ反映され、operations の証跡 ID を表示する。
- **レスポンシブ**: スマホ幅ではホーム（承認キュー）を最適化、深掘り画面は PC 幅を
  前提に設計してよい（無理な縮小で判断品質を落とさない）。
- **性能**: 一覧表示は初回表示（cold）で 1 秒以内・操作応答 300ms 以内を目標とし、
  測定条件（KW 1,000 件・記事 100 件・版 1,000 件の基準データセット、p95）を L3 で固定して
  受入時に実測する。
- **アクセシビリティ最低線**: キーボード操作可能・状態を色のみで表現しない。

## 5. 受入基準

1. **トレーサビリティ表**: UI の全表示フィールド→ §2 の表・列の対応表が設計成果物として
   存在し、対応のない表示フィールドが 0 件。
2. **「証跡なしでは空」**: 空 DB で起動した全画面が §1-2 の設計された空状態表示になる
   （ダミーデータ混入なし）ことを Playwright E2E で確認。
3. **一気通貫トレース**: 既知入力 1 件（KW 1 個）を取り込み→解析→ゲート→承認→公開まで
   流し、各工程の証跡（pipeline_runs/gate_runs/approval_requests/operations）が UI 上で
   追跡できることを E2E で確認。
4. **実データ疎通**: 稼働中の GSC過去28日 CSVとA8週次 CSVを取り込み、成果ビュー（3.7）とホーム（3.1）が
   実データで埋まる。
5. **操作証跡**: UI からの承認 1 件が approval_requests への応答として operations に記録され、
   導出状態が変化し、画面に証跡 ID が表示される E2E。
6. **スマホ承認**: スマホ幅でホーム→承認 1 件完了の E2E（判断要約が表示されること）。
7. **状態網羅試験**: 代表 2 画面でエラー状態・stale 状態を人工的に発生させ、設計された
   表示になることを確認。ホームから各画面の「問い」への到達が 2 クリック以内であることを
   画面遷移表で確認。
8. **セキュリティ最低線**（方式詳細は L3 で確定、以下は L2 受入条件）: 未認証アクセスは
   全 URL で拒否される／HTTP は HTTPS へ強制／noindex+robots 遮断（検索・AI クローラー
   非捕捉）／画面・ログ・DB に credential 値が出力されない／変更系リクエストは CSRF 対策と
   レート制限を持つ／本番 WP サイトとプロセス・認証を共有しない。
9. **スクリーンショット受入**: 全画面のスクリーンショットを受入証跡として保存し、
   画面ごとに §3 の「問い・表示・操作・受入」を判定項目としたチェックリストで PO が
   合否を返せる。

## 6. 非対象

- 複数ユーザー・権限管理（単一 PO。将来の製品化はレイヤを分けて別企画）。
- 通知配信（メール・プッシュ — カレンダーの外部通知は表示のみ。配信は後続スライス）。
- ⑦ クローラー計測・GA4 取り込みの実装（表示枠+「未計測」表示まで。実装は後続）。
- リライト閾値の確定（⑤）・記事パイプラインのスケジュール自走。
