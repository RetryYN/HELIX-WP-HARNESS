# L1 企画書 — 完全自走型 WP 運用 HARNESS

- 位置づけ: HELIX V モデルの L1 企画（フリー形式）。L2 要求の入力（目的・対象・価値仮説・採用境界）。
- 状態: **draft**（PO 確認前。confirm は PO の明示判断で行う）
- 日付: 2026-08-21

## 目的

WordPress サイトの運用（コンテンツ投稿・更新・計測・改善のループ）を、人間の
判断ポイントを承認ゲートに限定した上で **AI エージェントが完全自走**で回せる
ハーネスを作る。人間（PO）は方針と承認だけを持ち、日々の運用作業を持たない。

## 企画の柱（PO 定義 2026-08-21）

1. **既存運用からの引継ぎ**: 既存サイトの運用実態を取り込み、そこから運用ルールを作れる。
2. **新規サイトの立ち上げと運用**: 立ち上げから運用ループまでを一気通貫で回せる。
3. **HELIX-WP-THEME によるサイト構築**: テーマ開発ベースを使ってサイト構築ができる。

## 中核機能

- **解析基盤**を置き、SEO 施策・AIO/LLMO 施策（AI 検索・LLM 経由流入への最適化）が打てる。
  ニュースとオリジナルコンテンツの両方を扱える。
- **データ解析は原則 AI に依存せず、決定論的に計算で導く**（同じ入力から同じ結論が出る。
  AI は施策の生成・提案側に使い、判定・集計の正本にしない）。
- **データ取得**: GSC・GA4 はブラウザから確認し、定期取得は **UI の CSV エクスポートを
  落とす方式を正とする**（DOM スクレイピングはしない — CSV がそのまま決定論解析の入力になる）。
  無料の公式 API（Search Console API／GA4 Data API）への切替は**任意の上級オプション**に
  留める — GCP 側の設定（プロジェクト・API 有効化・認証情報）が大半のユーザーに高い障壁の
  ため前提にしない。使う場合は GCP 設定自体を有人ブラウザセッションで突破・代行できた
  環境に限る。
  キーワード・AI 関連の連携推奨 API は **DataForSEO**。
- **UI フロント**: データ確認と承認通知をフロントで行える。
  - 対象サイトの**サブドメイン**に作成し、サイトごとに個別に見られる。
  - **主サイトへ影響を及ぼさない**こと、**サーフェス Web に捕捉されない**こと
    （検索エンジン・クローラーに露出しない）を成立条件とする。

## 対象・非対象

| | 内容 |
| --- | --- |
| 対象 | WordPress 媒体の運用一式（投稿・更新・テーマ連携・計測取得・改善提案・再実行） |
| 対象 | **既存サイトの引継ぎ**（運用実態の取り込み→運用ルール化→運用移管） |
| 対象 | **新規サイトの立ち上げ**（環境構築→HELIX-WP-THEME 適用→初期コンテンツ→運用開始） |
| 対象 | 解析基盤・UI フロント（データ確認・承認通知）・SEO / AIO / LLMO 施策 |
| 対象サイト | HELIX 経由で運用する自社サイト。**検証も本番サイトで行う**（PO 判断 2026-08-21。専用検証環境は前提にしない） |
| 非対象 | WP 以外の媒体（X ほかは別リポの別ハーネス）。WP テーマ自体の開発（HELIX-WP-THEME 側の責務） |
| 非対象 | 第三者への配布・汎用パッケージ化 |

## 価値仮説

- 運用の人手コストがゼロに近づけば、サイト数・更新頻度をスケールさせても運用負荷が増えない。
- 判断を承認ゲートに集約することで、完全自走でも品質・安全（誤投稿・事故書込み）を
  fail-close で守れる。
- 運用ループ（投稿→計測→改善）を機械証跡で回すことで、改善が勘でなく evidence 駆動になる。

## 採用境界（すでに出ている PO 判断・上流制約）

1. **開発規律は HELIX コア（HELIX Lite）を継承**する。resident lanes / routing /
   allocation / 配布系は本家 HELIX-HARNESS で育て、本リポへ複製しない。
2. **進行順序は PoC → 要求 → 設計 → 実装**。実機証跡なしに先へ進まない
   （既存 PoC: XServer API 証跡 2026-08-14）。
3. **外部 write 境界**: 本番サイトへの write は承認ゲートを通す（自走段階に応じてゲート粒度を
   緩める。credential を repository・DB・ログへ書かないのは不変）。検証は本番サイトで行ってよい
   （PO 判断 2026-08-21 — 旧「Docker WP のみ」制約は本企画では採らない）。ただし破壊的操作
   （削除・上書き・設定変更）はバックアップ・ロールバック手段の確保を実行条件とする。
4. **対象基盤は XServer・接続は 4 車線**（PO 判断 2026-08-21）:
   **WP REST API**（コンテンツ運用の正本 — Application Password、旧 ADR-005 legacy 参照）／
   **WP-CLI**（REST で届かない WP 内部操作）／**XServer API**／**XServer CLI・SSH**
   （基盤操作: 引継ぎ・新規立ち上げ・環境構築。PoC 証跡 2026-08-14 の延長）。
   補完車線: 既知 URL への決定論的 HTTP fetch（レンダリング後の実表示確認 — URL 一覧は
   WP REST から得るためリンク発見クロールは不要）／DataForSEO（**代替不能な外部データに限定** — 検索ボリューム・SERP 順位・
   キーワード候補等。キャッシュと定期バッチで呼び出しを最小化する）／
   GSC・GA4 ブラウザ車線。
   記事制作時の**競合閲覧はコスト優先の段階方式**: ①自前の単発 HTTP fetch（無料・SERP 等で
   得た既知 URL のみ・巡回なし）→ ②ブラウザ車線 → ③DataForSEO Content Parsing（最後の手段）。
   **自前クローラーは作らない（明示 defer）** — 再入場条件は
   「DataForSEO と既知 URL fetch で賄えない監査要件が具体化した時」。
   他ホスティングへの対応は本企画の非対象（必要になったら別判断）。
5. **テーマ連携**: 開発ベースは HELIX-WP-THEME（旧 AGENT-NEO）。AI 判定ロジックは
   ハーネス（オーケストレーター）側に置き、テーマ／プラグインは表示に徹する
   （REQ-NF-025 の分離原則を引き継ぐ）。
6. **統合層との関係**: 本リポは HELIX-MARKETING-HARNESS（統合層）の `media/wp/`。
   共通規律は統合層 CLAUDE.md が正本。

7. **API 費用の最小化**（PO 判断 2026-08-21）: 無料車線（WP REST／CLI／SSH・ブラウザ・
   単発 fetch・GSC/GA4）を常に優先し、有料 API は代替不能なデータに限定する。有料呼び出しは
   キャッシュ・定期バッチ・呼び出し上限（config 値）で統制し、費用はダッシュボード等で可視化する。
   **AI 系計測（AI Overview／LLM 露出等の AIO/LLMO 観測）は自前観測が不可能なため
   DataForSEO 依存を例外として認める**。ただし最安運用を条件とする:
   live モードを使わず standard（task ベース）キューで取得／対象キーワードを重点セットに
   絞った低頻度の定期バッチ／結果キャッシュで同一データの再取得ゼロ。

8. **収益モデルは両対応**: サイトごとに自前サービス販売／アフィリエイト／併用を config で
   選択できる（ハーネスは特定モデルに固定しない）。アフィリエイトの ASP 提携申請・
   アカウント操作は API が無いためブラウザで行う。
9. **ブラウザ車線は有人／無人を区別する**（PO 判断 2026-08-21）:
   - **有人**（ユーザー同席セッション）: ASP 提携申請等の対外操作はここでのみ行う。
     同席が承認を兼ねるため別建ての承認ゲートは置かない。
   - **無人**（定期バッチ・自走中）: **リスクが無い操作に限る**（典型は GSC・GA4 等の
     データ取得）。対外的な契約・アカウント状態・主サイトに影響し得る操作は無人で行わない。
     リスク有無の判定基準（操作の分類）は L2 以降で確定する。

## 完全自走の到達段階（企画としての目標水準）

| 段階 | 内容 | 人間の関与 |
| --- | --- | --- |
| S1 | 指示駆動: PO の指示で個別運用タスクを実行し証跡を残す | タスクごとに指示 |
| S2 | 半自走: 運用ループを提案し、承認を得て実行する | 承認のみ |
| S3 | 完全自走: 承認ゲート付きでループを常時運転する | 例外時と方針変更のみ |
| S4 | 拡張: 既存サイトの引継ぎ・新規サイトの立ち上げを自走で実行できる | 引継ぎ/立ち上げの発注と承認 |

企画のゴールは S3、拡張目標が S4（引継ぎ・新規立ち上げ）。L2 以降のスライスは S1 から積む。
